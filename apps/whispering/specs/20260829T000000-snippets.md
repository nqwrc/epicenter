# Snippets: trigger-phrase expansion

**Status**: Draft
**Type**: Feature (new table, new pipeline stage)
**Scope**: `apps/whispering/src/lib/`, `apps/whispering/src/routes/(app)/(config)/`

## Problem

A dictated phrase that always expands to the same fixed text costs the same
breath every time. Saying a postal address, a signature block, or a standard
disclaimer is slower by voice than by keyboard, because the keyboard has text
expanders and dictation does not.

Snippets close that: speak a short trigger phrase, deliver the saved text.

## What a snippet is, and why it decides the design

A Dictionary entry is a hint. It tells the model a term exists and how it is
spelled, and a near miss still helps. Snippets are the opposite: the saved text
is a contract. An address with one street name altered, or a legal block with
one clause reworded, is worse than no expansion at all, because the damage is
plausible enough to ship.

That single property drives every decision below. Expansion must be exact,
which means it must be deterministic, which means it cannot be the model's job.

## Decision: a deterministic stage after Polish

Expansion is pure string substitution running on the polished transcript, after
`runPolish` and before delivery.

Three placements were considered.

**Prompt block, like Dictionary (rejected).** Hand the snippet table to the
model inside the Polish system prompt, consistent with ADR-0099. Rejected on
two counts: the model may paraphrase text that must be verbatim, and the whole
feature would stop working whenever Polish is off, which the user controls.

**Deterministic, before Polish (rejected).** Substituting on the raw transcript
matches triggers exactly as spoken, which is more reliable. It then feeds the
expanded text to Polish, which may reword the snippet body. That failure is
silent and corrupt: the output looks right and is wrong.

**Deterministic, after Polish (chosen).** Its failure mode is a trigger that
does not match, which surfaces as the literal words "my address" sitting in the
delivered text. The user sees it immediately and can fix it. A visible no-op
beats silent corruption of text the user deliberately saved verbatim.

The stated risk of this placement, that Polish rewrites a trigger before
matching sees it, is bounded by Polish's own scaffold. `buildPolishSystemPrompt`
pins meaning-preserving rules: no summarizing, no added words, no synonym swaps
(`operations/build-system-prompt.ts`). Polish will capitalize a trigger and add
a full stop. It is not licensed to turn "my address" into "my home address".
Case-insensitive matching with non-word boundaries absorbs exactly the changes
Polish is allowed to make.

This placement is also the only one where behavior is identical whether Polish
is on or off. One code path, one behavior to explain.

## Data model

A third table beside `recordings` and `recipes` in `workspace/index.ts`:

```
const snippetsTable = {
	trigger: field.string(),
	replacement: field.string(),
} as const;
```

Registered in `defineData({ tables: { recordings, recipes, snippets } })`, with
a `SnippetId` alongside `RecipeId`. Identity is the minted row id (ADR-0206).

Both fields are LWW values, which suits them: nobody edits a trigger phrase
character by character across two devices.

Deliberately absent, all present in the tool this borrows from:

- **Rich-text replacements.** Delivery is plain text.
- **Team sharing and personal-over-team precedence.** One user, no team.
- **Per-snippet enable flag.** An unwanted snippet is deleted. Dictionary sets
  the precedent by having no toggle either.
- **A global `snippetsEnabled` setting.** An empty table already means off.

## Matching semantics

`expandSnippets(text, snippets): string` in `operations/expand-snippets.ts`.
Pure by construction: no settings reads, no I/O, total (it cannot fail). This
mirrors `buildSystemPrompt` and makes the entire engine unit-testable without a
workspace or a model.

Four rules.

1. **Case-insensitive, longest trigger wins.** With both `my address` and
   `my work address` saved, the longer claims the match. Without this rule,
   registration order silently decides, which cannot be explained to a user.
   Two triggers of equal length that both match at the same position are
   ordered by row id, so the outcome is stable across runs and devices rather
   than dependent on table iteration order. The UI warns on exact duplicates
   so this tiebreak stays a safety net and not a feature.

2. **Single left-to-right pass. Inserted text is never rescanned.** This is
   what stops a replacement containing another trigger from expanding again,
   and what stops the `a -> b`, `b -> a` pair from hanging the pipeline.
   Cheap now, miserable to retrofit.

3. **Word boundaries are non-word characters, so adjacent punctuation still
   matches.** This departs from the tool this borrows from, which requires
   triggers to carry no adjacent punctuation. The departure is forced by the
   placement: running after Polish means "send my address" has already become
   "Send my address.", and a no-adjacent-punctuation rule would never match at
   the end of a sentence.

4. **Empty and whitespace-only triggers are inert**, so a half-typed row in the
   settings table cannot blank out random spans of text.

## Surface

A `snippets` route at `routes/(app)/(config)/snippets/+page.svelte`, with
`state/snippets.svelte.ts` and a `whispering/snippets.svelte.ts` accessor,
mirroring the recipes vertical. A flat table of trigger, replacement, delete.
Add-new appends an empty row.

Not in v1: search, sort, starring, bulk JSON import. Each answers a scale
problem, hundreds of shared team snippets, that a personal list of ten does not
have. Add search when the list makes its own case.

**Validation.** Warn on a duplicate trigger in the UI, not in the engine. The
engine stays total and resolves ambiguity by rule 1. Warning belongs where the
user can act; deterministic behavior belongs where they cannot.

## Error handling

There is none, by design. A total pure function over two strings has no failure
to report. That is the payoff for keeping expansion out of the model.

## Testing

`expand-snippets.test.ts` carries the weight, because the function is pure:

- single-trigger expansion, mid-sentence and at end of input
- case-insensitivity: "My Address" matches a lowercase saved trigger
- longest-wins across two overlapping triggers
- no rescanning: a replacement containing another trigger stays literal
- the `a -> b`, `b -> a` cycle terminates
- trailing punctuation still matches (this test is the justification for rule 3)
- partial words do not match: an `address` trigger leaves "addressable" alone
- empty trigger, empty table, and empty transcript are all no-ops

One integration test at the pipeline seam proves expansion runs after Polish and
still runs when Polish is off. That second half is the regression that would
otherwise ship unnoticed.

## Scope boundary

Snippets do not touch Polish, Dictionary, Recipes, or the prompt scaffold.
Nothing in ADR-0099 changes. The only edits to existing files are the table
registration in `workspace/index.ts` and one call in `operations/pipeline.ts`.
